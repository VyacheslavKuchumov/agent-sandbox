# Agent Sandbox — ограничения

Честный список того, от чего система **не** защищает, где у неё слабые места и что
неудобно. Формат пунктов: *в чём ограничение → чем грозит → что с этим делаем.*

## Коротко: что система НЕ делает
- **Не защищает от утечки данных через VPN.** Kill switch прячет твой реальный IP и
  не даёт агенту выйти в интернет напрямую. Но через VPN агент может отправить код или
  секреты на любой домен. Пока нет правил фильтрации, сайты не ограничены.
- **Не изолирует на уровне ядра.** Контейнер — это не виртуальная машина: ядро у всех общее.
- **Не проверяет код, который пишут агенты.** Всё, что они создают или предлагают и что
  ты потом запускаешь на хосте, выполняется уже с твоими правами.
- **Не даёт kill switch хосту** (это сознательное решение): при сбое VPN хост идёт напрямую.

## 1. Сеть и VPN

**1.1. Утечка данных через разрешённый канал.** Сейчас агент может отправлять данные
на любые сайты, только с IP VPN. Даже со списком разрешённых сайтов данные можно
унести через разрешённые: github.com, api.anthropic.com, pastebin-подобные сервисы.
→ Этап «ограничения»: правила sing-box для каждого агента. Полностью риск не снимается.

**1.2. Дашборд видит только домен, а не содержимое.** sing-box видит домен (SNI/Host),
IP, порт и объём. URL, тело запроса и заголовки HTTPS не видны: MITM мы сознательно не делаем.
Если включено ECH (Encrypted Client Hello), домен тоже скрыт и остаётся только IP.

**1.3. Работает только TCP через прокси.** Агенты выходят в интернет через HTTP/SOCKS-прокси:
- программы, которые не умеют работать через прокси, **просто не работают**, но
  утечки при этом нет;
- нет UDP/QUIC (HTTP/3 откатывается на HTTP/2) и ICMP (`ping` не работает);
- `git` по SSH (порт 22) напрямую не работает: нужен `ProxyCommand` через SOCKS или HTTPS-remote;
- внутри агента не работает локальный DNS. Инструменты, которые сначала сами резолвят
  имя, а потом подключаются по IP, без прокси работать не будут.

**1.4. Контейнер `vpn` — самое уязвимое место.** У него есть выход наружу и `NET_ADMIN`.
Уязвимость в sing-box (разбор протоколов на входе от агентов) может дать агенту
обход kill switch. → Входы sing-box слушают только порт прокси, sing-box регулярно
обновляется, контейнер работает с read-only rootfs.

**1.5. Одна точка отказа.** Если упал `vpn`, все агенты без интернета. Так задумано: так
работает fail-closed.

**1.6. IP сервера фиксируется при старте.** Адрес VLESS-сервера резолвится при запуске,
и firewall открывает только этот IP. Если IP сервера поменяется (DDNS, CDN), придётся
перезапустить `vpn`. Транспорты с CDN-фронтингом (WS через Cloudflare), где IP меняются,
работают нестабильно.

**1.7. Не все транспорты VLESS поддерживаются.** sing-box поддерживает tcp, ws, grpc,
httpupgrade, Reality и XTLS-Vision. **XHTTP/SplitHTTP (только в Xray) не поддерживается.**
Если твой ключ на xhttp, нужно поменять ядро на Xray (схема при этом не меняется).

**1.8. Общий внешний IP.** У всех агентов и хоста (через VPN) один и тот же IP выхода.
Внешний наблюдатель может связать их между собой.

**1.9. VPN-провайдер видит метаданные.** Владелец VLESS-сервера видит, куда ходят
агенты и хост (домены и объёмы).

**1.10. Нет IPv6 и локальной сети.** IPv6 отключён. Ресурсы, доступные только по IPv6,
недоступны. Устройства в домашней сети (NAS, роутер) агентам недоступны.

**1.11. Агенты изолированы друг от друга только сетью.** У каждого агента своя
internal-сеть, в которой есть только он и `vpn`. Друг друга агенты не видят. Но если
кто-то вручную подключит двух агентов к одной сети, изоляция между ними пропадёт.

## 2. Изоляция контейнеров (общее)

**2.1. Общее ядро.** Уязвимость в ядре или runc позволяет выйти из контейнера на хост.
→ Регулярные обновления `linux` и `docker`. Можно усилить:
`userns-remap` или gVisor (`runsc`) для coder/admin.

**2.2. Группа `docker` равна root.** Твой пользователь в группе `docker`, поэтому любой
процесс, запущенный от тебя на хосте, может управлять контейнерами с правами root. Агенты к
docker-сокету напрямую доступа не имеют, но любая вредоносная программа, запущенная от тебя, —
имеет. → Rootless Docker как возможное улучшение.

**2.3. Токены: украсть нельзя, использовать — можно.** Секретов в агентах нет: их держит
брокер `keys` и подставляет сам (ARCHITECTURE §3). Но пока агент работает, он может
**пользоваться** доступом через брокер в рамках политики: тратить лимиты LLM, пушить в
разрешённые репозитории. → Минимальные права у токенов (fine-grained PAT на конкретные
репозитории), политика путей и методов в брокере, лимиты, лог каждого запроса.
Ещё одно: брокер — единая точка, где лежат все секреты. Если взломать брокер, утекут все.
→ Минимальный код, read-only, без shell, сеть наружу только к allowlist API.
Подписка Claude/Codex через брокер ещё не проверена на практике (см. §3 архитектуры).

**2.4. Prompt injection.** Веб-страницы, issues, README и зависимости могут содержать
инструкции для агента. Песочница ограничивает *последствия*, но не сам факт.

**2.5. Цепочка поставок.** Пакеты npm/pip, которые ставит агент, выполняются внутри
контейнера. У них те же права, что у агента, в том числе на запись в `~/Projects`.

**2.6. Лимиты ресурсов.** Память, CPU и число процессов ограничены. Место на диске
в `~/Projects` и volumes **не ограничено**, агент может забить диск.

## 3. По типам агентов

### coder
**3.1. Опасный код в проектах.** Самый важный пункт. Агент пишет в `~/Projects`, а ты потом
работаешь с этими проектами на хосте. Опасность представляют: git hooks (`.git/hooks`),
`.envrc` (direnv), `Makefile`, `package.json` scripts, `.vscode/tasks.json`, конфиги IDE.
Всё это может выполниться **на хосте с твоими правами** и в обход VPN.
→ Собирать и запускать проекты внутри контейнера. Смотреть `git diff` перед запуском на
хосте. Не разрешать direnv автоматически. Глобально `core.hooksPath` на пустую папку.

**3.2. Секреты в проектах видны.** `.env`, ключи и токены в `~/Projects` агент читает.
→ Держать их вне `~/Projects`.

**3.3. Нет apt.** rootfs только для чтения, системные пакеты добавляются только через Dockerfile.

### infra
**3.4. Эскалация через ревью.** Агент правит `compose.yaml` и Dockerfile'ы. Если ты
применишь их не читая, он может выдать себе любые права: смонтировать `/`, подключить
docker.sock, добавить сеть с выходом в интернет. → `git diff` перед каждым `apply`.
Особое внимание: `volumes`, `privileged`, `cap_add`, `network_mode`, `networks`, `pid`, `devices`.

**3.5. `inspect` раскрывает env.** Через socket-proxy агент видит переменные окружения всех
контейнеров, включая чужие (например sima_*). → Секреты передавать файлами, а не через env.

**3.6. Сборка образов.** Сборка через обычный `docker build` выходит в интернет **напрямую**
(сеть bridge по умолчанию). Поэтому сборка идёт только через `bin/sandbox apply` и
builder в сети VPN. Ручной `docker build` в обход этого — дыра в kill switch для `RUN`.

**3.6a. infra не может перезапускать контейнеры.** В docker-socket-proxy v0.5.0 restart
требует `POST=1`, а это открыло бы `containers/create`. Поэтому у infra docker только на чтение,
перезапуски и пересборки — только через твой `bin/sandbox apply`.

### admin
**3.7. Видит больше, чем кажется.** Без root, но читает всё, что открыто на чтение всем:
- аргументы командной строки **всех** процессов хоста (`pid: host`). Если ты передаёшь
  токен аргументом (`--token=...`), агент его увидит;
- весь системный журнал (группы `systemd-journal`, `adm`), а в нём может оказаться личное;
- общедоступные файлы `/etc`, `/var`, `/host/tmp`.

`~` (права `700`) и файлы только для root (`shadow`, профили NetworkManager) **не видит**.

**3.8. Безопасность держится на `no-new-privileges`.** Корень хоста смонтирован с setuid-бинарями
(`/host/usr/bin/sudo`). Повысить права через них не даёт `no-new-privileges`
и read-only монтирование. Если убрать эту опцию, защиты не будет.

**3.8a. admin в группе твоего пользователя (gid 1000).** Это нужно, чтобы писать в `proposals/`.
Побочный эффект: он читает файлы хоста, доступные на чтение группе `kuchumov`. `~` закрыта правами `700`,
поэтому это в основном `/tmp` и подобные места. На WSL это касается и `/mnt/c` (см. WINDOWS.md §4).

**3.9. Предложения выполняешь ты.** Скрипт из `proposals/` выполняется с твоими правами
(часто через sudo). Kill switch и права агента на него не распространяются.

### assistant (почта и календарь)
**3.10. Prompt injection тут неизбежен.** Входящие письма пишут посторонние люди.
Защита строится не на том, что «модель не поддастся», а на том, что у захваченного агента
нет ни интернета, ни секретов, ни инструментов для необратимых действий без твоего одобрения.

**3.11. Утечка через то, что разрешено.** Захваченный агент может:
- положить чувствительные данные в **черновик** письма на адрес злоумышленника. Пока ты
  не одобришь отправку, письмо никуда не уходит. Но при одобрении «не глядя» уйдёт;
- исказить сводку: скрыть важное письмо или выдать фишинг за легитимное;
- поставить или снять ярлыки и заархивировать письма, то есть спрятать их от тебя
  (это обратимо, но можно не заметить).
→ Очередь одобрения показывает **полных получателей и полный текст**, плюс лог всех действий.

**3.12. Одобрение защищает, только пока ты его читаешь.** Если начать одобрять всё
подряд, защита пропадёт. Утомление от одобрений — реальный риск.

**3.13. Scope Google шире, чем нужно.** `gmail.modify` технически разрешает отправку.
Запрет отправки держится на `mailgw`, а не на Google. Если взломать `mailgw` или брокер,
токен позволит отправлять письма.

**3.14. Ограничения Claude Code (`managed-settings`) — мягкий слой.** Жёсткие слои — сеть,
отсутствие секретов и узкий набор инструментов `mailgw`. Если агент обойдёт настройки
Claude Code, у него всё равно нет ни сети, ни ключей.

**3.15. Одобрения только в терминале.** `bin/sandbox approvals` (CLI). Веб-страницы нет:
Docker не публикует порты из internal-сетей, а обычная сеть дала бы mailgw прямой выход.

**3.16. Google-токены лежат в шлюзах, а не в брокере.** `mailgw`/`drivegw` — детерминированный код
без LLM, но если взломать шлюз, утечёт его токен. Их выход в сеть ограничен `googleapis.com`.

### cad
**3.17. cad выполняет любой код в `~/3d-models`.** Blender и FreeCAD — полноценные Python-среды.
Если открыть на хосте `.blend` или `.FCStd`, созданный агентом, со включёнными скриптами (Blender:
Auto Run Python Scripts, FreeCAD: макросы), код выполнится на хосте. → Держи автозапуск скриптов
выключенным (в Blender по умолчанию выключен).

**3.18. Drive: scope `drive.file`.** Шлюз видит только файлы, которые создал сам: остальной диск
недоступен, но и загруженные вручную в ту же папку файлы он не увидит. Загрузка с тем же именем
заменяет содержимое (версии хранит Drive). Удалять агент не может, только ты.

## 4. Хост, OpenSnitch, мониторинг

**4.1. Kill switch хоста нет (так задумано).** При сбое VPN watcher переключает хост
напрямую: виден реальный IP, DNS идёт через провайдера.

**4.2. Окно переключения.** Пока watcher не заметил сбой (несколько секунд), трафик хоста
идёт в мёртвый туннель и связи нет. Если сам watcher упал, при сбое VPN хост остаётся
**без интернета**, пока ты не выключишь профиль вручную.

**4.3. Петли маршрутизации.** Полный туннель через NM требует исключений: IP сервера,
сети Docker, LAN. Если новая сеть Docker не попадёт в исключения, она уйдёт в туннель.
На хосте уже есть `tun0` (172.18.0.1/30, другой VPN-клиент?). Два полных туннеля
одновременно будут конфликтовать.

**4.3a. Двойной туннель.** Сейчас на хосте активен `tun0`. Соединение `vpn`-контейнера с
VLESS-сервером идёт через маршрутизацию хоста, то есть, возможно, через этот второй VPN.
Работать будет, но задержка выше, а IP, с которого видно подключение к VLESS-серверу, —
это IP того VPN.

**4.4. OpenSnitch в режиме мониторинга ничего не блокирует.** Всё разрешено, только логируется.
Его можно обойти: root-процессы, сырые сокеты, трафик ядра. Он не видит трафик контейнеров.
Если в браузере включён DoH, OpenSnitch видит только IP, а не домен.

**4.5. Логи — это история твоего браузинга.** Loki хранит, куда ходили ты и агенты.
Данные лежат локально. → Ограничить срок хранения (например 30 дней) и закрыть
Grafana паролем, хоть она и слушает только `127.0.0.1`.

**4.5a. Сеть мониторинга не internal.** Docker не публикует порты из internal-сетей,
поэтому `sbx-monitor` — обычный bridge: Grafana, Loki и Vector технически могут выйти в интернет
напрямую. Телеметрия и проверка обновлений Grafana и Loki выключены. Агенты в эту сеть не входят.
Grafana на `127.0.0.1:3300`: порт 3000 у тебя занят.

**4.5b. IPv6 хоста идёт мимо туннеля.** В NM-профиле `ipv6.method=disabled` только для WG-интерфейса.
Если у провайдера есть IPv6, сайты с IPv6 пойдут напрямую. Если это важно, отключи IPv6 на wlan0.

**4.6. Сопоставление «программа ↔ домен ↔ VPN» приблизительное.** События OpenSnitch и
sing-box связываются по времени и адресу назначения, общего идентификатора у них нет.

## 5. Удобство и функциональность

**5.1. herdr видит агента только по экрану.** Интеграции и хуки внутри контейнеров не
ставятся (сокет herdr не пробрасывается), поэтому восстановление сессий работает хуже,
а статус определяется по экрану.

**5.2. Авторизация.** Логин идёт в одноразовом контейнере (`bin/sandbox login`):
ссылка открывается в браузере хоста, код вставляется вручную. Callback на `localhost` из
контейнера не работает. Работа подписки Claude/Codex через брокер ещё не проверена.

**5.3. Автообновление агентов.** Обновлять `claude`/`codex` в read-only rootfs нельзя.
Обновление — пересборка образа (`bin/sandbox apply`) или установка в `$HOME` агента.

**5.3a. Встроенная песочница Codex выключена.** bwrap не может создать namespace при
`cap_drop: ALL` и seccomp Docker, поэтому `bin/agent` запускает `codex --sandbox danger-full-access`.
Границей служит сам контейнер (read-only rootfs, нет секретов, сеть только через VPN).

**5.4. Нет GUI и браузера в контейнерах.** Playwright и headless Chrome — только если
добавить их в образ (и они тоже пойдут через прокси).

**5.4a. Нет buildx.** Плагин `docker-buildx` не установлен, сборка идёт классическим
builder'ом. Для сборки через VPN-сеть (§3.6) нужен `pacman -S docker-buildx`.

**5.4b. Сборка образов идёт напрямую.** `bin/sandbox rebuild/update/apply` собирают образы на хосте
классическим builder'ом, и `RUN apt/npm/pip` ходят в интернет мимо VPN. Пока buildx не установлен,
это так. Собирать запускаешь только ты, агенты этого не могут.

**5.4c. Версии.** `bin/sandbox update` берёт только стабильные релизы старше 14 дней. GitHub API без
токена ограничен 60 запросами в час, поэтому при `gh` в системе передаётся `gh auth token`.

**5.5. Docker внутри агентов недоступен.** coder не может запускать `docker compose` для своих
проектов (иначе это был бы root на хосте). Варианты на будущее: rootless DinD/Sysbox или
отдельный sandbox-docker без доступа к хосту.
