# DESIGN-01 — короткое визуальное и UX-ревью v1

Контекст: `feat/electron-control-center`, PR #1. Изучены `AGENTS.md`, `docs/gui-state.md`, все три файла `desktop/renderer/`. Оба изображения `desktop/artifacts/demo.png` и `demo-compact.png` просмотрены через `view_image`. Приложение и команды управления не запускались. Скриншоты показывают только демо, успешное действие и верх страницы; выводы об ошибках, фокусе и поведении сделаны по renderer и контракту в state-файле. Интерактивная доступность и соответствие WCAG не подтверждены.

Общая оценка: основа понятная — устойчивое левое меню, хорошо различимые заголовки, единые карточки, текстовые статусы и заметное основное действие. Демо явно обозначено. Но первый экран отдаёт слишком много места служебной информации, а различие между запуском контейнера и открытием CLI требует знания системы. Главный приоритет — сделать путь к работе и результат действия однозначными.

## 1. P1 — объяснить связь «Запустить» и «Открыть терминал»

**Основание.** На `demo.png` у остановленного Admin яркая кнопка терминала доступна одновременно с «Запустить». Из скрина непонятно, нужно ли сначала запускать контейнер. По коду `updateDisabled()` разрешает launch для stopped, а автоматический запуск объясняет только `title`. `execute()` использует общее «Выполнено» и для launch; по контракту `gui-state.md` успешный запрос терминала ещё не подтверждает успех CLI.

**Место и изменение.** `app.js`: `createAgent()`, `updateDisabled()`, `execute()`; карточка агента. Показать постоянную короткую подпись «Откроет CLI в отдельном терминале; окружение запустится при необходимости». Для stopped уточнить основную кнопку: «Запустить и открыть CLI»; отдельный start — «Запустить окружение». Для web сохранить отдельное объяснение новой сессии. Успешный ответ launch обозначать «Запрос на открытие терминала отправлен».

**Влияние.** Пользователь понимает последствия основного действия и не принимает отправленный запрос за работоспособную сессию.

**Acceptance checks.** На синтетических running/stopped/web карточках без hover ясно, что откроется и будет ли запуск. Доступное имя кнопки содержит агента и смысл действия. После успешного launch нигде не утверждается успешный запуск CLI; отказ и отмена различимы.

## 2. P1 — поднять рабочие действия на первый экран, особенно при 900 px

**Основание.** На широком скрине между верхней панелью и карточками стоят демобаннер, заголовок, результат команды и четыре сводки; нижние кнопки карточек уже обрезаны краем кадра. В компактном скрине виден лишь верх карточек. Сводка «Автообновление» визуально равна состоянию агентов, хотя нужна реже. По CSS при ширине 900 CSS px сохраняются sidebar 200 px, четыре сводки и две колонки агентов: после боковых отступов остаётся около 650 px контента до учёта scrollbar. Переключение сводки на две колонки и сворачивание sidebar происходят только при ≤850 px. State-файл сообщает smoke 900×700 без overflow; это не доказывает удобство первого экрана. Размеры файлов скриншотов не принимались за CSS viewport.

**Место и изменение.** `index.html`: `.summary-grid`, `.page-heading`, `#demo-banner`; `styles.css`: `main`, `.summary-card`, media queries; `app.js`: `showView()`. На вкладке «Агенты» сократить сводку до компактной строки; интервал опроса перенести к времени обновления. Сжать демобаннер, сохранив явное предупреждение. На ширине 900 px уменьшить долю навигации и разрешить перенос заголовка/статуса. На «Журналах» и «Ключах» общая сводка не должна отодвигать профильное содержимое.

**Влияние.** Быстрее доступ к агентам, меньше прокрутки и конкурирующих акцентов; метаданные не приходится уменьшать ради размещения.

**Acceptance checks.** В демо при 900×700 CSS px на вкладке «Агенты» полностью видны имя, состояние, выбор инструмента и основная кнопка первого агента. На всех вкладках нет горизонтального overflow, перекрытий и обрезанных подписей. При увеличении масштаба до 200% всё доступно прокруткой и клавиатурой. Сравнить также широкий viewport и 850 px на границе адаптации.

## 3. P1 — сохранять видимость ошибок и актуальности данных при прокрутке

**Основание.** Скриншоты показывают успешное состояние; ошибок на них нет. По коду `#status-error` находится наверху, а `#command-status` — внизу страницы. `execute()` сообщает результат через них и `#action-notice`, но локальной обратной связи у карточки нет. В catch `refreshSnapshot()` сохраняет старые карточки и предупреждает об этом только верхним текстом. Во время опроса `snapshotBusy` отключает управление; причина отключения рядом с карточкой не объясняется.

**Место и изменение.** `app.js`: `execute()`, `refreshSnapshot()`, `updateDisabled()`; `index.html`: уведомления. Показывать рядом с затронутым агентом краткий результат/ошибку и переход к полному выводу. Для сохранённых данных явно отмечать «Устаревшие данные» с временем последнего успеха в доступном при прокрутке статусе. Для блокировки пояснять причину: обновление, выполнение команды или недоступность состояния; оставить понятный повтор обновления.

**Влияние.** Пользователь не теряет отказ за пределами viewport и не принимает старое зелёное состояние за текущее.

**Acceptance checks.** На синтетических ошибках snapshot/run/launch, тайм-ауте и отмене из середины длинного списка видны результат и следующий шаг. При сбое опроса старые данные помечены, управление заблокировано с объяснением; после успешного обновления пометка снята. Отмена отличается от ошибки, ожидание не выглядит как окончательный отказ.

## 4. P2 — усилить читаемость рабочих метаданных

**Основание.** На обоих скринах вторичные подписи заметно слабее заголовков; особенно мелки контейнер и здоровье на широком скрине. По CSS `.agent-meta` и `.summary-detail` имеют 10 px, ряд служебных подписей — 8–11 px. Это риск чтения на обычном масштабе; численные значения контраста не измерялись, нарушение WCAG по скрину не заявляется.

**Место и изменение.** `styles.css`: `.agent-meta`, `.summary-detail`, `.infra-info p`, `.console-meta`, `.pill`. Поднять рабочие метаданные до 12–13 px и проверить контраст на реальных фонах. Уменьшать декоративные отступы раньше шрифта. Сохранить текстовые обозначения состояний, а не полагаться на зелёный/красный.

**Влияние.** Контейнер, здоровье и диагностика читаются без увеличения масштаба; легче отличать stopped от unavailable и unhealthy.

**Acceptance checks.** Измеренный контраст обычного значимого текста ≥4.5:1. На 900 px и 100% масштабе метаданные читаются без hover; длинные имена и ошибки переносятся без потери содержимого. Статусы различимы в монохроме. Неактивные элементы оценивать отдельно: их низкая яркость сама по себе не доказывает нарушение контрастных требований.

## 5. P2 — завершить доступность повторяющихся контролов и уведомлений

**Основание.** По коду уже есть `lang="ru"`, skip-link, focus-visible, label/select, `aria-current`, alert для ошибки состояния и live-status результата команды. Но все select называются одинаково — «Инструмент»; article не связан с именем агента через `aria-labelledby`. Основной `#action-notice` не является live-region; `showView()` не переводит фокус и не объявляет новый заголовок. Это потенциальные трудности для скринридера, а не наблюдавшийся отказ.

**Место и изменение.** `app.js`: `createAgent()`, `showView()`; `index.html`: `#action-notice`. Дать карточкам программное имя, select — имя с агентом. Объявлять начало и итог действия через один стабильный live-region, исключив дублирование с существующим status. При смене раздела обеспечить предсказуемое объявление заголовка и положение фокуса.

**Влияние.** Пользователь клавиатуры и скринридера понимает, каким агентом управляет и что изменилось после действия.

**Acceptance checks.** Пройти в демо Tab/Shift+Tab/Enter/Space: меню → карточка → инструмент → действие → вывод; фокус виден и не теряется при опросе. Скринридер сообщает имя агента у каждого select, новый раздел и один итог команды. Повторный опрос не переобъявляет всю страницу. Skip-link приводит к основному содержимому.
